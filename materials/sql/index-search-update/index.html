索引には、顧客IDと注文表の行の場所が入っています。 注文が2件の例では、顧客4242の索引から注文 #308 と #18000 の行へ直接たどれます。

顧客ID順に並んでいるので、次の索引が4243なら、4242の注文はそこで終わりです。顧客4243の注文行は読みません。

顧客4242の注文を見つけても、同じ顧客の注文がほかにないか確認します。 このSQLは、条件に合う行をすべて返す指定です。注文表には同じ顧客の注文が離れて並ぶこともあるので、索引なしでは末尾まで調べます。

重複する列にも索引を作れます。 同じ人が何度注文しても顧客IDは同じです。注文番号は注文ごとに異なり、主キーとして使えます。顧客IDで注文履歴をよく探し、少数の注文に絞れるなら索引の候補です。 PostgreSQLの一意インデックス

注文表と索引は、説明用に一部を抜き出しています。下のSQL演習は、顧客4242の注文が2件ある場合です。

✏️ 注文の追加時は、注文表と索引の両方に反映します。索引には更新の手間と保存容量がかかります。

DBはデータの件数や値の分布をもとに、読み取りの手間を見積もります。何％なら索引を使うという一律の基準はありません。

⌨️ 操作

「実行計画を比べる」を押すと、ブラウザー内のPostgreSQLで下のSQLを実行します。演習結果の②と③を見比べると、同じ顧客IDのインデックスがあっても、2件と4万9千件ではDBが選ぶ探し方が変わることを確認できます。

① 索引なし・2件
② 索引あり・2件
③ 索引あり・多くの行
実行するSQL（PostgreSQL）
BEGIN;
CREATE TEMP TABLE index_lesson_orders AS
SELECT n AS order_no,
       CASE WHEN n IN (308, 18000) THEN 4242
            WHEN n = 4242 THEN 308
            ELSE n END AS customer_id
FROM generate_series(1, 50000) AS n;
ANALYZE index_lesson_orders;

-- ① 索引なし
EXPLAIN (COSTS OFF)
SELECT * FROM index_lesson_orders WHERE customer_id = 4242;

-- ② 索引あり
CREATE INDEX ON index_lesson_orders (customer_id);
ANALYZE index_lesson_orders;
EXPLAIN (COSTS OFF)
SELECT * FROM index_lesson_orders WHERE customer_id = 4242;

-- ③ 多くの行が該当する場合
EXPLAIN (COSTS OFF)
SELECT * FROM index_lesson_orders WHERE customer_id <= 49000;
ROLLBACK;

📋 結果を見てみよう（表示例）

表示例
① Seq Scan on index_lesson_orders
     Filter: (customer_id = 4242)

② Index Scan using index_lesson_orders_customer_id_idx on index_lesson_orders
     Index Cond: (customer_id = 4242)

③ Seq Scan on index_lesson_orders
     Filter: (customer_id <= 49000)

Seq Scanは表を順に読む、Index Scan / Index Only Scan などは索引を使う計画です。③のように多くの行が対象だと、索引を作ってもSeq Scanが選ばれることがあります。版や統計情報で表示は変わります。

✅ 答え

人は、よく使う検索で少数の行に絞れる列を候補にします。DBは、検索ごとに索引を使う場合と注文表を順に読む場合の手間を比べます。

まとめ

実際に近い件数・値の偏りを練習用DBに用意し、実行計画・検索時間・更新時間・索引の容量を作成前後で比べます。EXPLAINだけでは実測時間は出ません。
