インデックスとは？検索と更新のトレードオフ

5万件の注文から1件を探すとき、索引があるとデータベースの探し方がどう変わるかを比べます。

図で仕組みを理解しよう

🔎 5万件の注文表から、注文番号 4242 を探します。

📄 インデックスなし

注文表を先頭から末尾まで確認

1…4242…50000

確認する注文表の行 50,000行

📇 インデックスあり

番号順の索引で、注文の場所を絞る

📇 索引で 1 〜 10000 の範囲へ ↓ 4242 がある索引項目へ 📄 注文表の 4242 へ直接移動

確認する注文表の行 該当の1行

注文表の残りを読み飛ばせるので、1件を探すのが速くなります。

索引を使って注文の詳細を取り出す流れを簡略化した図です。下の演習では注文番号だけを取得するため、索引だけで結果を返せる実行計画も候補になります。

✏️ 注文の追加時は、注文表と索引の両方に反映します。検索が速くなる一方、更新の手間と保存容量が増えます。

❓ 疑問

検索が速くなるなら、すべての列にインデックスを作るとよい？

💡 理由

索引があると少数の行を探しやすくなります。一方、行の追加や索引対象の値の変更時には、テーブルに加えて索引の維持も必要です。索引を保存する容量も増えます。多くの行を読む場合などは、データベースが索引を使わずに表を順に読むことがあります。

⌨️ 操作

架空の注文5万件から1件を探します。「実行計画を比べる」を押すと、ブラウザー内のPostgreSQLで下のSQLを実行します。

① 索引なし・1件
② 索引あり・1件
③ 索引あり・多くの行
実行するSQL（PostgreSQL）
BEGIN;
CREATE TEMP TABLE index_lesson_orders AS
SELECT n AS order_no FROM generate_series(1, 50000) AS n;
ANALYZE index_lesson_orders;

-- ① 索引なし
EXPLAIN (COSTS OFF)
SELECT * FROM index_lesson_orders WHERE order_no = 4242;

-- ② 索引あり
CREATE INDEX ON index_lesson_orders (order_no);
ANALYZE index_lesson_orders;
EXPLAIN (COSTS OFF)
SELECT * FROM index_lesson_orders WHERE order_no = 4242;

-- ③ 多くの行が該当する場合
EXPLAIN (COSTS OFF)
SELECT * FROM index_lesson_orders WHERE order_no <= 49000;
ROLLBACK;

📋 結果を見てみよう（表示例）

表示例
① Seq Scan on index_lesson_orders
     Filter: (order_no = 4242)

② Index Only Scan using index_lesson_orders_order_no_idx on index_lesson_orders
     Index Cond: (order_no = 4242)

③ Seq Scan on index_lesson_orders
     Filter: (order_no <= 49000)

Seq Scanは表を順に読む、Index Scan / Index Only Scan などは索引を使う計画です。③のように多くの行が対象だと、索引を作ってもSeq Scanが選ばれることがあります。版や統計情報で表示は変わります。

✅ 答え

よく使う絞り込み条件を候補にし、あわせて登録や更新への影響を確かめて決めます。

まとめ

実際に近い件数・値の偏りを練習用DBに用意し、実行計画・検索時間・更新時間・索引の容量を作成前後で比べます。EXPLAINだけでは実測時間は出ません。
