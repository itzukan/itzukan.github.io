CHAPTER 02 / 16

Webサイトはなぜ攻撃される？

機密性は情報を勝手に見せないこと。完全性は勝手に変更させないこと。可用性は必要なときに使えること。りんごショップの注文履歴・価格・サービス稼働に対応します。

📊 図解で確認

機密性＝注文履歴の漏えい防止／完全性＝価格改ざん防止／可用性＝注文機能の継続

❓ 確認問題：商品価格の改ざんで損なわれる性質は？

✓ 完全性です。

CHAPTER 03 / 16

HTTPSとは？

HTTPSはTLSで通信を保護し、途中の盗み見や改ざんを防ぎます。接続先の証明書も検証します。ただし偽サイトもHTTPSを利用できるため、通信の保護とお店の信頼性は別です。

📊 図解で確認

利用者 ⇄ HTTPS（暗号化） ⇄ ショップ。偽ショップでもHTTPSを利用できる。

❓ 確認問題：HTTPSなら偽サイトではない？

✓ いいえ。URLや運営元も確認します。

CHAPTER 04 / 16

認証と認可の違い

認証は「あなたは誰か」の確認。認可は「何をしてよいか」の確認。Aさんがログインできても、Bさんの注文履歴を見てよいわけではありません。

📊 図解で確認

Aさん → ログイン認証 → 注文101（A所有：許可）／注文102（B所有：拒否）

❓ 確認問題：他人の注文を拒否するのは認証？認可？

✓ 認可です。

CHAPTER 05 / 16

パスワードの守り方

パスワードをそのまま保存すると漏えい時に危険です。Argon2idなどの専用パスワードハッシュ方式と利用者ごとのソルトを使います。SHA-256を1回かけるだけでは不十分です。多要素認証も役立ちます。

📊 図解で確認

平文保存 ✕ → 専用ハッシュ＋個別ソルト ○ → 多要素認証で追加防御

❓ 確認問題：SHA-256を1回使えば十分？

✓ いいえ。専用方式を使います。

CHAPTER 06 / 16

Cookieとセッション

ログイン後、ブラウザはセッションIDをCookieで送信し、サーバーはログイン状態を照合します。SecureはHTTPS送信、HttpOnlyはJavaScriptからの読み取り制限、SameSiteは他サイトからの送信条件の制御です。

📊 図解で確認

ブラウザ［Cookie: セッションID］ → サーバー［ログイン状態を確認］

❓ 確認問題：HttpOnlyでJavaScriptはCookieを読める？

✓ 読めません。ただしブラウザからの送信を全面禁止する属性ではありません。

CHAPTER 07 / 16

XSSとは？

レビューに入力された文字をHTMLとして解釈すると、意図しないスクリプトなどが動作する恐れがあります。これがXSSです。HTMLタグが太字になるだけではXSSとは限りませんが、信頼できない入力のHTML解釈は危険です。

📊 図解で確認

入力：<b>おいしい！</b> → HTMLとして解釈：太字／テキストとして表示：タグも文字

❓ 確認問題：レビュー入力を無条件にHTMLとして扱ってよい？

✓ いいえ。

CHAPTER 08 / 16

XSSを防ぐには？

HTMLを許可しないレビュー本文はtextContentで表示します。innerHTMLに信頼できない文字列を直接渡すと危険です。HTMLが必要なら適切なサニタイズを行い、CSPも追加の防御として検討します。

📊 図解で確認

安全：review.textContent = userInput; ／ 危険：review.innerHTML = userInput;

❓ 確認問題：文章だけを表示するならtextContentとinnerHTMLのどちら？

✓ textContentです。

CHAPTER 09 / 16

SQLインジェクションとは？

商品検索の入力値をSQL文に直接連結すると、入力内容がSQLの構造を変えてしまう場合があります。これがSQLインジェクションです。入力を命令として解釈させない設計が重要です。

📊 図解で確認

検索文字列 → 危険な文字列連結 → SQLの構造が変わる恐れ

❓ 確認問題：SQLを使うこと自体が危険？

✓ いいえ。入力を命令と混ぜる実装が危険です。

CHAPTER 10 / 16

SQLインジェクションを防ぐには？

プレースホルダーを使い、SQLの構造と入力値を分離します。たとえば SELECT * FROM products WHERE id = ? に対し、商品IDを別の値として渡します。

📊 図解で確認

SQL構造：SELECT * FROM products WHERE id = ? ／ 値：input

❓ 確認問題：入力値はSQLに直接連結する？

✓ いいえ。パラメータ化クエリを使います。

CHAPTER 11 / 16

CSRFとは？

Aさんがログイン中に別サイトを開くと、意図しない操作のリクエストが送られ、Cookieも送られる条件ではサーバーが本人の操作と誤解する場合があります。CSRFトークン、SameSite、Origin検証などを適切に組み合わせます。

📊 図解で確認

Aさんログイン中 → 別サイト → 意図しない注文変更 → CSRF対策で検証

❓ 確認問題：ログイン済みのリクエストは必ず本人の意思？

✓ いいえ。CSRFの可能性があります。

CHAPTER 12 / 16

CORSとは？

Web画面 https://shop.example からAPI https://api.example にGET /productsを送る例です。APIが正常応答しても、適切なCORS許可ヘッダーがなければブラウザのJavaScriptは応答を読めません。curlには同じ制限がありません。CORSは認証・認可の代わりではありません。

📊 図解で確認

shop.example → GET /products → api.example → 許可ヘッダーなし：JSで読めない／許可あり：読める

❓ 確認問題：CORSエラーならAPI処理は必ず失敗？

✓ いいえ。応答の読み取り制限の場合があります。

入力チェックだけで安全？

注文数0を画面で禁止しても、APIへ直接リクエストできます。サーバー側でも数値や範囲を検証し、操作権限も別に確認します。

📊 図解で確認

画面：quantity=0を拒否 → API直送の可能性 → サーバーでも拒否

❓ 確認問題：画面で検証すればサーバー側は不要？

✓ いいえ。

Aさんの注文101とBさんの注文102。AさんがGET /orders/102を送っても、サーバーは注文の所有者を確認して拒否しなければなりません。オブジェクト単位の認可不備はBOLAと呼ばれます。IDをランダムにするだけでは防げません。

まとめ・次の学習

安全なWebサイトには、HTTPS、認証と認可、パスワードの適切な保存、XSS・SQLインジェクション・CSRF対策、サーバー側の入力検証が必要です。依存ライブラリの更新、監視、バックアップなども忘れずに。
