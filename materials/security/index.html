CHAPTER 02 / 16

Webサイトはなぜ攻撃される？

機密性は情報を勝手に見せないこと。完全性は勝手に変更させないこと。可用性は必要なときに使えること。りんごショップの注文履歴・価格・サービス稼働に対応します。

📊 りんごショップで図解
🔒 機密性他人の注文履歴を見せない
→
🛡️ 完全性商品価格を勝手に変えさせない
→
🟢 可用性注文機能を使い続けられる
❓ 確認問題：商品価格の改ざんで損なわれる性質は？

✓ 正解：完全性です。

🛡️ 推奨する対応：価格など重要な値はサーバー側で管理し、変更権限も確認します。

💡 理由：利用者が送った価格をそのまま信じると、改ざんされる恐れがあります。

CHAPTER 03 / 16

HTTPSとは？

HTTPSはTLSで通信を保護し、途中の盗み見や改ざんを防ぎます。接続先の証明書も検証します。ただし偽サイトもHTTPSを利用できるため、通信の保護とお店の信頼性は別です。

📊 りんごショップで図解
🧑 利用者ブラウザ
→
🔐 HTTPS / TLS通信を暗号化・証明書を確認
→
🍎 りんごショップ通信先のサイト
❓ 確認問題：HTTPSなら偽サイトではない？

✓ 正解：いいえ。HTTPSだけでは本物のサイトと断定できません。

🛡️ 推奨する対応：URLのドメイン名や運営元を確認し、不審なリンクからのログインを避けます。

💡 理由：偽サイトも自分のドメインでHTTPSを使えます。

CHAPTER 04 / 16

認証と認可の違い

認証は「あなたは誰か」の確認。認可は「何をしてよいか」の確認。Aさんがログインできても、Bさんの注文履歴を見てよいわけではありません。

📊 りんごショップで図解
👤 Aさんログイン成功＝認証
→
📦 注文101Aさんの注文 → 許可
→
📦 注文102Bさんの注文 → 拒否
❓ 確認問題：他人の注文を拒否するのは認証？認可？

✓ 正解：認可です。

🛡️ 推奨する対応：ログイン確認に加え、注文ごとに本人が閲覧できるかをサーバー側で判定します。

💡 理由：認証済みでも、他人の注文へのアクセス権があるとは限りません。

パスワードの守り方

パスワードをそのまま保存すると漏えい時に危険です。Argon2idなどの専用パスワードハッシュ方式と利用者ごとのソルトを使います。SHA-256を1回かけるだけでは不十分です。多要素認証も役立ちます。

📊 りんごショップで図解
❌ 平文保存パスワードがそのまま残る
→
✅ 専用ハッシュ＋ソルトArgon2idなどで保存
→
➕ 多要素認証ログインを追加保護
❓ 確認問題：SHA-256を1回使えば十分？

✓ 正解：いいえ。SHA-256を1回適用するだけでは不十分です。

🛡️ 推奨する対応：Argon2idなどのパスワード保存専用方式を、個別ソルトと適切な設定で使います。

💡 理由：高速な一般用途ハッシュだけでは、漏えい時に推測を試されやすくなります。

🛡️ 推奨する対応：セッションCookieには原則Secure・HttpOnly・適切なSameSiteを設定します。

💡 理由：HttpOnlyだけでCSRFなどの問題がすべて防げるわけではありません。

CHAPTER 07 / 16

XSSとは？（Cross-Site Scripting／クロスサイトスクリプティング）

レビューコメントに入力された文字をHTMLとして解釈すると、意図しないスクリプトなどが動作する恐れがあります。これがXSSです。HTMLタグが太字になるだけではXSSとは限りませんが、信頼できない入力のHTML解釈は危険です。

📊 りんごショップで図解
📝 レビューコメント入力<b>おいしい！</b>
→
⚠️ HTMLとして扱うタグが書式として解釈される
→
✅ 文字として扱うタグもそのまま文字になる
❓ 確認問題：レビューコメント入力を無条件にHTMLとして扱ってよい？

✓ 正解：いいえ。レビューコメントを無条件にHTMLとして解釈してはいけません。

🛡️ 推奨する対応：HTMLが不要ならtextContentなどで文字として表示し、必要な場合は適切にサニタイズします。

💡 理由：信頼できない入力をHTMLとして扱うと、XSSにつながる恐れがあります。

SQLインジェクションとは？

商品検索の入力値をSQL文に直接連結すると、入力内容がSQLの構造を変えてしまう場合があります。これがSQLインジェクションです。入力を命令として解釈させない設計が重要です。

📊 りんごショップで図解

🛡️ 推奨する対応：利用者の入力はSQL文に直接連結せず、パラメータ化クエリで渡します。

CSRFとは？

Aさんがログイン中に別サイトを開くと、意図しない操作のリクエストが送られ、Cookieも送られる条件ではサーバーが本人の操作と誤解する場合があります。CSRFトークン、SameSite、Origin検証などを適切に組み合わせます。

📊 りんごショップで図解
🧑 Aさんショップにログイン中
→
🌐 別サイト意図しない操作を誘導
→
🛡️ ショップCSRFトークン等で検証
❓ 確認問題：ログイン済みのリクエストは必ず本人の意思？

✓ 正解：いいえ。ログイン済みでも本人の意思とは限りません。

🛡️ 推奨する対応：状態変更リクエストにはCSRFトークン等の対策を行い、SameSiteやOrigin確認も適切に組み合わせます。

💡 理由：別サイトから意図しない操作を誘導される場合があります。

CORSとは？

Web画面 https://shop.example からAPI https://api.example にGET /productsを送る例です。APIが正常応答しても、適切なCORS許可ヘッダーがなければブラウザのJavaScriptは応答を読めません。curlには同じ制限がありません。CORSは認証・認可の代わりではありません。

❓ 確認問題：CORSエラーならAPI処理は必ず失敗？

✓ 正解：いいえ。API自体は正常に応答している場合があります。

🛡️ 推奨する対応：APIのHTTP応答とブラウザのCORSエラーを分けて調べ、必要なオリジンだけを許可します。

💡 理由：CORSは主にブラウザがJavaScriptへ応答を渡せるかを制御する仕組みです。

🧪 演習④ CORSの応答を比較

shop.exampleのJavaScriptがapi.exampleへGET /productsを送信。APIは正常に応答しています。

CORSの条件を選んでください。ネットワーク通信は行わない概念シミュレーションです。
